# ADR-0029: 💡 capture の秘匿判定をチャンネル権限へ一元化し、recall を優先する

- ステータス: accepted(2026-08-13)
- 日付: 2026-08-13
- 関連: ADR-0018(可視性ゲート)/ ADR-0027(抽出品質)/ design.md §6.4 ③-a・§9.3

## 背景

実運用で「💡 を付けても何も起きない」報告があった。bot は正常に動作しており、門番
(`prompts/capture/triage.md`・fast モデル)が下記の理由で `capture: false` にしていた:

- 「結論が確定していない進行中の議論」
- 「NDA 関連情報も含まれる」

調査の結果、次が判明した:

1. **「NDA」という語はリポジトリに存在しない**。原因は triage.md の
   「未公開の対外情報・法務センシティブ」という抽象語で、モデルがこれを NDA 相当と解釈していた。
   この 2 語は **design.md §9.3 の限定列挙**(人事評価・処遇・給与・採用候補者個人情報 / 健康・私生活 /
   **経営が指定した**営業機密 / 認証情報そのもの)に**無い独自拡張**であり、capture の triage・draft と
   gap/entry の 3 ファイルにしか存在しない。
2. 「迷ったら **false**」(triage.md)が増幅器として働き、曖昧なケースをすべて落としていた。
3. **未確定の扱いが二重基準**だった。extractor は `guards.ts` で「情報は失わず、確定だけさせない」
   (未確定 decision → open question へ降格)なのに、capture の triage だけは逃がし先が無く全捨て。
4. `capture: false` は **DM も返信も出さない**ため、ユーザーからは故障と区別できない
   (レート超過・既存 PR の場合は DM するのに triage 落ちだけ無音)。
5. 秘匿判定の機械実装は存在せず、§9.3 の実効的な唯一の実装がこのプロンプト 1 行だった。

一方 **ADR-0018 で信頼境界は既にチャンネル権限に移っている**:
「bot を private チャンネルに招く = そのチャンネルを stratum に読ませる」。
読ませたくないものは Discord の権限か `permanent_exclude` で止まる。
triage の秘匿判定はその**三重目**であり、唯一「人間の承認を経ない・監査不能・偽陰性が見えない」層だった。

## 決定

### D1. 秘匿判定はチャンネル権限に一元化する

プロンプトによる秘匿判定は **生の認証情報(トークン・パスワード・API キー等)のみ**に縮小する。
人事・給与・健康・顧客名・契約金額・未公開の対外情報は、**bot に見えているチャンネルにある限り
記録してよい**。秘匿の境界は Discord のチャンネル権限と `channels.yaml` の `permanent_exclude`
(ADR-0018 D3)であり、そこを通過した内容を再度モデルに検閲させない。

### D2. 未確定でも捨てずに残す

結論が出ていない議論も「検討中の記録」として capture する(選択肢・論点・現時点の傾向)。
draft 側で `confidence: low` を付け、「決まったこと / まだ決まっていないこと」を書き分ける。
`verification_status: "unverified"`(ADR-0027 D4)+ 人間の 👍 承認が既に二段ゲートとして効いている。
extractor の「情報は失わず、確定だけさせない」と同じ思想に揃える。

### D3. 迷ったら true(recall 優先)

「取りこぼしの方が安い」を反転する。誤検知は人間が 👍 しなければ捨てられる(コスト = PR 1 本の
レビュー)が、**取りこぼしは誰も気づけない** — gap-tracker が埋めるのは「質問された未回答」だけで、
💡 の取りこぼしは永久に埋まらない。人間が明示的に 💡 を付けた時点で「残す意思」は表明されている。

### D4. 見送りは理由を DM で返す

`capture: false` のときリアクションした本人に理由を DM する(無音をやめる)。
「要点をまとめ直して 💡 を付け直すと通ることがある」の案内を添える。

### 適用範囲

**💡 capture のみ**(+ 文面の整合のため gap の回答エントリ生成)。
extractor / qa / pr-miner / interview の §9.3 規定(4 カテゴリの完全除外)は**現状維持**する
— 議事録の自動抽出は人が 1 件ずつ選んでいないため、従来の慎重さを保つ。

## 影響・トレードオフ

- **利点**: 💡 が「押しても無反応」に見える問題の解消。検討中の議論・顧客案件の情報も蓄積される。
  秘匿の境界が「チャンネルに bot が居るか」の 1 点になり、人間が理解・監査しやすい。
- **コスト**: ノイズ PR が増えうる(人間が 👍 しなければ捨てられる。頻発するなら triage の
  「成立しない例」を運用しながら調整する)。KB に未確定・機微寄りの内容が入るため、
  **KB リポジトリ自体のアクセス管理が実質的な秘匿境界になる**(既にそうだが、比重が増す)。
- 認証情報の除外だけは残るが、機械検出は無い(§9.3 の「伏字化して警告」は未実装のまま)。

## 却下した代替案

- **全プロンプト一括で緩和**: 議事録の自動抽出(extractor)は人が選んでいないため、慎重さを残す。
- **triage の三値化**(capture / defer / reject): スキーマ変更に見合う運用上の利益が現時点で無い。
  v1 は二値 + 理由 DM で様子を見る。
- **秘匿検出の機械ガード実装**(正規表現で NDA 等を検出): D1 の方針(チャンネル権限に一元化)と
  真っ向から矛盾する。

## design.md 転記リスト(人間)

- §9.3: 「💡 capture は例外として、除外は生の認証情報のみ(秘匿はチャンネル権限で管理・ADR-0018)」を追記。
- §6.4 ③-a: 「収集対象チャンネルは allowlist 制」の記述は ADR-0018 で失効済み(可視性ベースへ)。
  併せて「未確定の議論も検討中の記録として capture する」を追記。
