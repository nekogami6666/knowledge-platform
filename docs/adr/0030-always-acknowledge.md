# ADR-0030: 無言経路の一掃(操作には必ず応答を返す)

- ステータス: accepted(2026-08-13)
- 日付: 2026-08-13
- 関連: ADR-0018(可視性ゲート)/ ADR-0029(capture の見送り理由 DM)/ design.md §6.3・§6.4・§6.5

## 背景

ADR-0029 で「💡 の見送りを DM で返す」1 経路だけを塞いだが、同じ形の無言経路が bot 全体に残っている。
コードを棚卸ししたところ、ユーザーが**明示的に操作したのに何の応答も返らない**経路が 4 種類あった。

1. **ack の非対称**。元メッセージにリアクション ack を付けるのは gap 回答の捕捉(`discord.ts`)と
   voice-memo の受付(`voice.ts`)だけ。💡 capture と VC 録音には ack が無く、「押した / 喋った」
   直後にフィードバックが何も無い。
2. **DM 依存**。capture の `tryDm` / voice-pipeline / vc-recorder は DM 失敗を握りつぶしてログのみ。
   DM を閉じている人にはその機能が**丸ごと無言**になる(承認導線が DM 👍 なので機能自体が死ぬ)。
3. **例外が無言**。capture・voice-pipeline・interview-pipeline の catch はログのみ。
   ユーザーからは「壊れている」と「対象外だった」の区別が付かない。
4. **機能 OFF が無言**。設定・認証・STT キーのいずれかが欠けていると早期 return する
   (capture / voice / VC / 代理マージ / `/interview`)。運用中の設定漏れが誰にも見えない。
5. **拒否理由が無言**。代理マージの guard(not-ops-channel / not-webhook-message / repo-not-allowed)と
   gap 回答の未捕捉(not-webhook-reference / no-question-id)は、reason 文字列を作るだけで捨てている。

いずれも「bot は正常、ユーザーには故障に見える」形であり、ADR-0029 の背景と同一の失敗である。
個別対応ではなく横断の方針として決める。

## 決定

### D1. リアクション ack を全入口に

ユーザー操作(リアクション・投稿)を受け取る入口は、**元メッセージへのリアクション**で状態を返す。

| 記号 | 意味 | 例 |
| --- | --- | --- |
| ✅ | 受理(処理が完了した / 既に完了していた) | capture の PR 作成成功・voice-memo の受付 |
| ⏳ | 保留(キューに残り、後で自動的に再試行される) | pipeline の一時的失敗 |
| ⚠️ | 見送り・失敗(このままでは処理されない) | triage 見送り・恒久失敗・機能 OFF |

reply ではなくリアクションを基本にするのは、チャンネルを汚さずに「届いた」ことを示せるため。
**ack の失敗で本処理を落とさない**(権限不足で `react` できない環境がある)。失敗は warn ログのみ。

### D2. DM 失敗を握りつぶさない

DM 送信に失敗したら、**元メッセージへの返信**で最低限の理由を返す(共通関数 `notifyUser`)。
返信も失敗したら warn ログ(そこから先は打つ手が無い)。DM を閉じている人でも、
自分の操作の結果が本人に見える場所に必ず 1 回は出る。

### D3. 例外は必ずユーザーに返す

catch でログだけして黙るのをやめる。`isTransient`(429/529/timeout 等)で 2 分岐する。

- **一時的**: 再試行の主体で文面を変える。
  - pending が残る経路(voice-pipeline / interview-pipeline)= 「あとで自動的に再試行します」+ ⏳。
  - **再試行の仕組みが無い経路(💡 capture)= 「少し時間をおいて 💡 を付け直してください」+ ⚠️**。
    キューが無いのに「自動的に再試行します」と言うのは嘘なので、文面を分ける。
- **恒久**: 「処理できませんでした: <理由の要約>」+ ⚠️。理由は `Error.message` の先頭 200 字程度に
  切り詰めた 1 行。秘密は載せない(ログの (A) スクラブは Discord 送信には効かないため、
  例外メッセージに秘密を混ぜないのは throw 側の責務)。

同じ一時的失敗が再試行のたびに通知されないよう、通知は**アクション単位で 1 日 1 回**に抑制する。

### D4. 機能 OFF は静かに落とさず一度だけ案内

必要な設定・認証が欠けている入口では、操作した本人に
「この機能は現在利用できません(設定が未完了です)。管理者に連絡してください。」を返す。
連投で鬱陶しくならないよう、**同一ユーザー・同一機能で 1 日 1 回**に抑制する
(`store.hitRateLimit(subject, "feature-off-notice:<機能>", jstDayKey(now), 1)` を流用。
capture の日次上限と同じ仕組み・同じ JST 日バケット)。

**通知先を特定できない入口は対象外**とし、起動時のログ・警告に倒す。具体的には:

- **VC 入室**(`discord.ts` の VoiceStateUpdate): 元メッセージも interaction も無く、
  「誰に返すか」が決まらない。起動時に `{ vcRecorder: false }` を info ログで出す。
- **voice-memo の `channel_id` が未設定**: 専用チャンネルが分からない以上、どの投稿が
  「音声メモの操作」なのか判定できない。全チャンネルの音声添付に反応させるのは害の方が大きい。
- **`/interview` の deps 未注入**: `commandsToRegister` がコマンド自体を登録しないため
  (ADR-0028 D5)、ユーザーからはコマンドが存在せず「無反応」にならない。現状維持。

### D5. 拒否理由の明示

reason 文字列を**ユーザー向け日本語**へ写す純関数を置き、拒否時に短く返す。ただし
**「操作の意図が明確なときだけ」**返す — 👍 や返信は通常運用で大量に発生するため、
無条件に返すとチャンネルが荒れる。

- **代理マージ**: 「👍 × 人間 × 本文に GitHub PR URL がある」ときのみ理由を返す。
  not-ops-channel / not-webhook-message / repo-not-allowed / ops-config-off(= gh 未設定含む)を写像し、
  not-thumbsup / bot-reactor / no-pr-url は `null`(通知不要)。
- **gap 回答**: 「返信先が bot / webhook の投稿(かつ自 bot の投稿ではない)」ときのみ返す。
  人間同士の返信・bot 自身の記録返信(voice 訂正フライホイール)には無反応のまま。
  さらに `no-question-id` は**返信先が依頼らしい(q-ID 形の文字列を含む)ときだけ**返す —
  extractor の PR 通知など q-ID を持たない webhook 投稿への雑談返信にまで
  「回答として受け取れませんでした」と返すのは誤案内であり、ops チャンネルが荒れる。

### D6. 管理者向けの可視化

`warmDmChannels` の個別失敗を集計し、起動ログに `{ dmWarmFailed: n }` を出す。
DM を開けない人が居ると DM 👍 の承認導線が死ぬため、管理者が起動時に気づけるようにする。

## 影響・トレードオフ

- **利点**: 「操作したのに無反応」が原理的に無くなる。故障と対象外が区別できる。
  設定漏れが運用中に発見される(これまでは無言で機能が死んでいた)。
- **コスト**: リアクション・返信・DM の送信が増える(Discord API 呼び出しは操作あたり 1〜2 回)。
  抑制(1 日 1 回)を入れてもノイズはゼロにならない。D5 の「意図が明確なときだけ」で線を引く。
- **残るリスク**: 恒久失敗の理由要約は例外メッセージ由来のため、秘密を含む例外を投げる実装が
  あれば Discord に漏れうる。長期的には送信前スクラブを共通化する余地がある。

## 却下した代替案

- **全部 reply で返す**: 通常運用の 👍・返信の量に対して reply は多すぎる。チャンネルが荒れて
  かえって読まれなくなる。ack はリアクション、理由は必要なときだけ短い返信 / DM に分ける。
- **現状維持(ログだけ見る)**: ログを見るのは管理者だけで、操作した本人には永久に届かない。
  ADR-0029 で同じ判断を 1 経路だけ覆したのに、他を放置する理由が無い。
- **無反応の理由を全部 DM**: DM を閉じている人に届かない(まさに塞ぎたい穴)。D2 の
  「DM → 元メッセージ返信」のフォールバックを共通化する方を採る。
