# ADR-0038: Discord メッセージ本文を /ask の検索対象にする(本文の保存・同期・質問者の権限での絞り込み)

- ステータス: proposed
- 日付: 2026-10-01
- 関連: ADR-0017 D7(本文保存の禁止 — 本 ADR で /ask 検索用に限り置き換える)・
  ADR-0033 D6(extractor の fetch → extract → discard)・ADR-0018(チャンネル可視性ゲート・permanent_exclude)・
  ADR-0006 D2 / ADR-0037 D1(エージェントの能力面・`mcpServers` 未設定の方針 — 本 ADR で 1 点だけ例外を置く)・
  ADR-0034(/ask は ephemeral)・ADR-0035(時間予算)・design.md §1.3 / §4.6 / §5.4 / §9.2 / §9.3 / §9.5
- 備考: design.md は保護パスのため、下記「design.md への転記」は人間レビューで行う。

## 背景

/ask が答えられるのは KB・議事録・リポジトリに書かれたことだけで、Discord のチャンネルで直近に交わされた
議論や決定は、誰かが 💡 で捕捉するか extractor(ADR-0033)が週 2 回・cap 付きで KB 化するまで検索できない。
利用者からは「昨日 #dev で決めた件」「先週の障害の話」のような直近の議論を聞きたいという要望がある。

これまでは ADR-0017 D7 が「メッセージ本文は残さない(§9.3 をデータ構造で遮断)」と定め、ADR-0033 D6 も
これに従って本文を永続させてこなかった。**2026-10-01 のオーナー決定**で、/ask の検索に使う目的に限って
Discord 本文を保存し検索可能にすることが承認された。条件は次の 3 つ:

1. `permanent_exclude` のチャンネルと design.md §9.3 の機微情報の除外は**緩めない**。
2. 質問者は、**自分が Discord 上で閲覧できない本文**に由来する回答・引用を決して受け取らない。
3. ADR-0017 / ADR-0033 は経緯として残し、変更は本 ADR に記録する。

## 決定

### D1. 本文の保存は「/ask の検索用」に限り許可する(ADR-0017 D7 の一部置き換え)

- ADR-0017 D7 の「保存は集計値のみでメッセージ本文は残さない」のうち、**/ask の検索インデックスとしての保存だけ**を
  許可する。expertise-mapper の集計(D7 の本来の対象)が本文を使ってよいという意味ではない。
- 保存した本文を読むのは discord-bot プロセス内の検索ツール(D6)だけ。他のアプリ・バッチ・KB へは出さない。
  ホスト側 timer(gap-tracker・freshness・extractor-discord)もこのファイルを読まない。
- ADR-0033(extractor)は**現行どおり** fetch → extract → discard のまま変えない。将来、extractor が REST で
  取り直す代わりにこの保存済み本文から読む選択肢はあるが、本 ADR の範囲外(別 ADR。bot と extractor の
  プロセス・ホストをまたぐため、ファイル共有の方式から決める必要がある)。
- 本機能は **`discord-index.yaml` の `enabled: true` で明示的に有効化**する。既定は OFF で、OFF のときは
  DB ファイルを作らず、イベントも購読せず、/ask の挙動も変わらない。

### D2. 保存先は bot.db とは別の SQLite ファイル(`DISCORD_INDEX_DB_PATH`・コンテナ内 `/data/discord-index.db`)

- bot.db はホストの timer(gap-tracker・freshness・stats)と WAL で共有しているため、書き込み頻度の高い
  メッセージ同期を同居させない。保持期間の削除・ロールバック(ファイル削除)も独立して行える。
- `/data` はエージェントの cwd(`/clones`)の外であり、ADR-0037 の読み取り封じ込めによりエージェントは
  このファイルを直接 Read できない。エージェントが本文に触れる経路は D6 のツールだけに限る。
- 表(better-sqlite3・`user_version` でマイグレーション):
  - `messages`: `id INTEGER PRIMARY KEY`(FTS の rowid 用の安定キー)・`message_id`(UNIQUE)・`guild_id`・
    `channel_id`(メッセージが属するチャンネル。スレッドならスレッド ID)・`parent_channel_id`(可視性の判定単位 =
    トップレベルのチャンネル。スレッドなら親、通常チャンネルなら自分)・`thread_id`(スレッドのみ)・
    `author_id`・`author_name`(保存時点の表示名)・`created_at`・`edited_at`(epoch ms)・`content`・`permalink`
  - `channels`: チャンネルごとの名前・種別・親とカーソル(`last_message_id` = そこまで連続取得済みの snowflake)
  - `tombstones`: 直近に削除したメッセージ ID(同期中の古い取得結果で削除済みの本文を復活させないため。1 日で破棄)
  - `messages_fts`: FTS5(`tokenize='trigram'`)。**外部コンテンツ表**(`content='messages'`)+ トリガで同期する。
- FTS5 の方式の選択:
  - 外部コンテンツ表にするのは、本文を 2 重に持たず(ディスク)、検索結果の本文を `messages` から取れるため。
    `messages` の rowid は `INTEGER PRIMARY KEY` にして VACUUM でも変わらないようにする(外部コンテンツ表の前提)。
  - contentless(`content=''`)は列値を返せず、削除に `contentless_delete`(新しめの SQLite)が要るため採らない。
- trigram は 3 文字未満の語に一致しない(実機で確認済み)。1〜2 文字の語(「勤怠」「DB」等)は `LIKE` で補う。
  3 文字以上の語は FTS、短い語は LIKE とし、両方ある質問では AND で組み合わせる。
- これは**語の一致による全文検索**であり、design.md §5.4 の embedding / ベクトル検索ではない
  (§5.4 の移行判断基準・§1.3 の非目標には触れない)。

### D3. 同期: イベント + 起動時の取り込み + 定期照合

- **イベント**(bot の常駐 Gateway。intents は既存の Guilds / GuildMessages / MessageContent で足りる):
  - `MessageCreate` / `MessageUpdate`: 保存対象(D4)なら upsert。編集で空本文になった等、対象外になったら削除。
    編集は `edited_at` が保存済みより古い取得結果で上書きしない。
  - `MessageDelete` / `MessageBulkDelete`: 削除(+ tombstone)。判定なしで常に行う(消す方向は安全)。
  - `ThreadDelete` / `ChannelDelete`: そのチャンネル(とスレッド)の本文を削除。
  - `ChannelUpdate` / `GuildRoleUpdate` / `GuildRoleDelete` / 自分の `GuildMemberUpdate`: 可視性を再評価し、
    bot が見えなくなったチャンネルの本文を削除する(権限の上書きの変更は ChannelUpdate で届く)。
  - `ThreadCreate`: 公開スレッドのメタデータを登録する(本文は MessageCreate で入る)。
- **起動時の取り込み**: チャンネルごとにカーソルから `after` で REST ページング(`collector-session.ts` の
  `paginateAfter` を共用)。カーソルが無ければ `now − backfill_days`(既定 90 日 = extractor と同じ)から。
  チャンネルは直列に処理し、429 は discord.js の内部キューに任せる。1 回の取得は
  `max_fetch_per_channel`(既定 10,000 件)で打ち切り、残りは次の周期でカーソルから続ける。
  - カーソルは**REST で連続取得できた位置だけ**を表し、ライブイベントでは進めない(イベントで進めると、
    停止中の取りこぼし区間を飛ばしてしまうため)。
- **定期照合**(`reconcile_interval_hours` 既定 6 時間ごと・起動時にも 1 回): 直近 `reconcile_window_days`
  (既定 7 日)を取り直し、編集を反映し、取得結果に無い保存済みメッセージ(= 停止中に削除されたもの)を削除する。
  削除判定は「取得開始時刻より前に作られ、かつ取得範囲に含まれる ID」に限る(取得中に届いた新規メッセージを
  消さない)。同じ周期で保持期間(`retention_days` 既定 180 日)を過ぎた本文と古い tombstone を削除する。
- 対象外(v1): アーカイブ済みスレッドの停止中の編集・削除(稼働中の削除イベントは反映される。本文は保持期間で消える)。

### D4. 保存時の可視性: 「bot に見える」∧「permanent_exclude でない」

- 保存するのは、ギルドのテキストチャンネル(通常・アナウンス)と、その公開スレッド・フォーラム投稿
  (公開スレッド)のメッセージで、`isChannelAllowed`(ADR-0018: bot の実効 ViewChannel ∧ ¬permanent_exclude。
  スレッドは親 ID でも照合)を満たすものだけ。スレッドは**スレッド自身と親チャンネルの両方**が通ること
  (カテゴリ単位の除外が親経由で効くようにする)。
- **private thread は v1 では保存しない**: 質問者がそのスレッドに参加しているかを bot 側で確実に判定できない
  (参加者一覧の取得に追加の権限・API 呼び出しが要る)。
- bot・webhook・システムメッセージと空本文(添付のみ等)は保存しない(bot 自身の出力を再び検索対象に
  しない・ノイズを減らす)。
- bot が見えなくなった・permanent_exclude に入ったチャンネルの本文は削除する(イベント時と定期照合時)。
  permanent_exclude の変更は再起動で反映されるため、起動時の照合で削除される。
- ギルドが一時的に unavailable の間は、誤って全削除しないよう可視性による削除を見送る。

### D5. 質問時の可視性: 質問者が閲覧できるチャンネルだけを検索する

- /ask のたびに、interaction の member とギルドのキャッシュ(ロール・チャンネルの権限上書き)から、
  **質問者が `ViewChannel` と `ReadMessageHistory` の両方を持つトップレベルのチャンネル**を計算する。
  計算は Discord の標準アルゴリズム(owner → @everyone + ロールの合算 → Administrator → @everyone の上書き →
  ロールの上書きの合算 → メンバー個別の上書き)を純関数で実装する(ADR-0018 D6 の REST 版と同じ考え方)。
  - 公開スレッドは親チャンネルの権限に従う(Discord の仕様)。private thread は保存していない(D4)。
  - 質問者の Administrator は Discord 上で全チャンネルを閲覧できるため、全チャンネル可視として扱う。
  - bot 側も同じ関数で「今 bot が見えるか(`checkAdmin:false` 相当・ViewChannel のみ)∧ ¬permanent_exclude」を
    再計算し、**検索範囲 = 質問者に見える ∩ いま bot に見える**とする(保存時のゲートと削除の遅れに対する
    二重の防御)。
  - 判定できない場合(DM・ギルド未キャッシュ・member 不明)は検索範囲を空にし、ツールを渡さない。
- 質問の時点で計算するため、権限の変更は次の /ask から効く(キャッシュは Gateway のイベントで更新される)。
- 限界: ギルドのキャッシュが Discord 側の実状態より遅れる瞬間はありうる(イベント配送の遅延)。
  ロールの付け外し直後の数秒は旧権限で判定されうる。

### D6. エージェントへの渡し方: 読み取り専用のプロセス内ツール 1 本(ADR-0006 / ADR-0037 への例外)

- エージェントは DB ファイルを直接読めない(D2)。代わりに、Agent SDK のプロセス内 MCP サーバ
  (`createSdkMcpServer` + `tool()`・SDK 0.3.285 で型と実行時の export を確認済み)で
  **`discord_search(query, since?, until?, channel?)` の 1 本だけ**を渡す。
  - 返すのは、検索範囲(D5)内で一致した最大 `max_results` 件(既定 20)の抜粋(本文を短く切ったもの)・
    作成者の表示名・チャンネル名・作成日時・permalink。
  - SQL は固定のプリペアドステートメントで、検索語は FTS のフレーズ(引用符で囲む)と LIKE のパラメータとして
    渡す(FTS の構文や SQL をモデルが組み立てる余地は無い)。書き込み・削除の経路は無い。
  - 今回の /ask でツールが返した permalink を記録し、引用の検証(D7)に使う。
  - ツールは /ask の要求ごとに作り直し、その質問者の検索範囲を閉じ込める(他の要求と共有しない)。
- `runAgentSearch`(`packages/llm`)は、**呼び出し元がプロセス内ツールを渡したときだけ** `mcpServers` に
  それを載せる。載せ方は固定:
  - サーバ名は固定(`stratum`)で、`strictMcpConfig: true`(外部の MCP 設定を読まない)。
  - `tools`(基本ツール集合)は従来どおり Read / Grep / Glob のまま。プロセス内ツールは `allowedTools` に
    `mcp__stratum__<name>` として個別に加える(`permissionMode: "dontAsk"` のため、許可していないツールは使えない)。
  - ツール検索で遅延ロードされないよう `alwaysLoad` を付ける(ToolSearch は基本ツール集合に無いため)。
  - ADR-0037 の PreToolUse hook(ファイル系ツールだけを判定)と `blockReadsOutsideWorkingDirectories` は
    そのまま効く。このツールはファイルパスを受け取らないため hook の対象外で、到達範囲を広げない。
- **ADR-0006 D2 / ADR-0037 D1 の「`mcpServers` は未設定のまま維持」の例外**とする理由:
  - 懸念の本体は「任意のプロセスや外部サーバを起動・接続し、能力と到達範囲を広げる」ことだった。
    プロセス内ツールは bot 自身のコードで、読み取り専用・固定クエリ・件数上限・質問者の権限による絞り込みを
    コードで強制する。
  - 別案(エージェントに DB ファイルを読ませる・検索結果をプロンプトに事前に詰める)より面が小さい。
    前者は ADR-0037 の封じ込めに穴を開け、後者は質問に関係ない本文まで毎回モデルに渡す。
  - 例外は「呼び出し元が明示的に渡したプロセス内ツールだけ」に限る。stdio / HTTP / SSE の MCP サーバ、
    `agents`・`canUseTool`・`toolAliases`・`additionalDirectories` は引き続き未設定。
    /ask 以外の呼び出し元(capture・voice・extractor 等)はツールを渡さないため、挙動は変わらない。

### D7. 引用の検証: 今回ツールが返した permalink だけを受け付ける

- 機能が有効な /ask では、`validateCitations` は discord 引用を「形式が正しい」かつ「**今回の要求でツールが返した
  permalink の集合に含まれる**」ものだけ通す。ツールは質問者に見えるものしか返さない(D5)ため、
  引用はすべて質問者に見えるメッセージになる。それ以外(モデルが KB の本文などから写した URL・捏造した URL)は
  破棄する。
- 機能が OFF の /ask は従来どおり(形式のみの検証)。未公開の本文がそもそもモデルに渡らないため。
  ON のときと同じ厳格化を OFF にも適用するかは未決事項とする。

### D8. 機微情報(§9.3)

- **コードでの自動判定(分類器)は無い。** §9.3 の 4 カテゴリ(人事評価・処遇・給与・採用候補者の個人情報 /
  健康・私生活 / 経営指定の営業機密 / 認証情報)は、従来どおりプロンプト(qa/answer)で抽出・引用・要約を禁止する。
- 保存段階で効くのは `permanent_exclude`(経営指定のチャンネル・スレッドは親でも照合)と bot の可視性だけで、
  これは緩めない。機微な話題は permanent_exclude のチャンネルか、bot を入れない private チャンネルで行う運用を
  維持する(ADR-0018 D5 の周知に「/ask で本文が検索される」ことを加える)。
- 残るリスク: 公開チャンネルに書かれた認証情報や個人情報は保存され、質問者に見えるなら検索結果としてモデルに
  渡る。回答への転記はプロンプトで禁じるが、確率的な防御である。削除されたメッセージはイベントまたは照合で消える。
- `queries.answer`(bot.db)には、回答に要約・引用された本文が残りうる。bot.db は従来から全利用者の質問と
  回答を持つ機微なファイルとして扱っている(ADR-0037)。

### D9. 設定(`discord-index.yaml`・bot の config ディレクトリ)と既定値

| キー | 既定 | 理由 |
|---|---|---|
| `enabled` | `false` | 明示的に有効化するまで何もしない(本番への反映はオーナーの指示後) |
| `backfill_days` | 90 | extractor(ADR-0033 D9)・§9.2 の「直近 90 日」と揃える |
| `retention_days` | 180 | 半期前までの議論を検索できる範囲。古い本文を持ち続けない。`backfill_days` 以上であること |
| `reconcile_interval_hours` | 6 | 停止中の編集・削除を半日以内に反映しつつ、REST 呼び出しを抑える |
| `reconcile_window_days` | 7 | 編集・削除の大半は投稿から数日以内。`retention_days` 以下であること |
| `max_results` | 20 | 1 回の検索でモデルに渡す本文量の上限(トークン・露出面を抑える) |
| `max_fetch_per_channel` | 10000 | 1 周期でチャンネルあたりに取得する上限(初回取り込みが長引いても周期を塞がない) |

DB のパスは env `DISCORD_INDEX_DB_PATH`(コンテナの既定 `/data/discord-index.db`)。

### D10. ロールバック

1. `discord-index.yaml` の `enabled: false` にして bot を再起動する(ツールは渡されず、同期も止まる)。
2. `~/stratum/data/discord-index.db`(と `-wal` / `-shm`)を削除する。本文はこのファイルにしか無い。
   bot.db・KB・カーソル以外の状態には影響しない。

## 影響・トレードオフ

- **利点**: 直近の議論・決定を /ask で出典付きで答えられる。KB 化(💡・extractor)を待たずに済む。
- **露出面**: 本文が VM のディスクに最大 180 日残る(従来は Discord 上にしか無かった)。VM のバックアップ・
  ディスクの扱いは bot.db と同等以上に慎重にする。
- **権限の正しさは Discord の権限モデルとキャッシュに依存する**: 質問時の計算は Discord の標準アルゴリズムに
  従うが、Discord 側の仕様変更(新しい権限の概念)には追随が要る。
- **ディスク**: 1 日 500 件・平均 150 字として 180 日で約 9 万件。本文 + メタデータ + trigram 索引で
  100MB 未満の見込み(実測で確認する)。
- **REST 負荷**: 6 時間ごとにチャンネル数 ×(直近 7 日分 ÷ 100)回程度。20 チャンネル・1 日 500 件なら
  1 周期 40 回前後。
- **プロンプト**: qa/answer を v6 に上げ、discord_search を使う場面(KB・議事録に無い直近の議論・決定)と、
  Discord の引用はツールが返した permalink を使うことを指示する。

## 却下した代替案

- **bot.db に同居させる**: ホストのバッチとの WAL 競合・削除とロールバックの独立性(D2)。
- **エージェントに DB ファイルを Read させる / clones 配下に本文を書き出す**: ADR-0037 の封じ込めに穴を開け、
  質問者の権限で絞れない(cwd 配下は全員に読める)。
- **検索結果を system prompt に事前に詰める**: 質問に関係ない本文まで毎回渡し、何を検索するかをモデルが
  決められない。
- **外部 MCP サーバ(stdio)として実装**: 別プロセス・別の到達範囲を増やす。プロセス内ツールで足りる。
- **embedding / ベクトル検索**: design.md §5.4 の判断基準を満たしていない。語の一致で始める。
- **質問者の可視性を保存時に決める(チャンネル ACL を複製)**: 権限の変更に追随できない。質問時に計算する。
- **private thread を含める**: 参加者の判定ができないため v1 では除外(未決事項)。

## 未決事項

1. private thread を対象にするか(参加者一覧の取得と質問時の照合が要る)。
2. 機能 OFF の /ask でも discord 引用を厳格化するか(D7)。

## 追記(2026-10-08): 速さのための上限と事前検索の受け皿

- ステータス: proposed
- 関連: ADR-0035(時間予算)・ADR-0041「System One 判定層」(起票予定・事前検索と関連度ゲートの本体)

### 背景

有効化の準備で /ask の所要時間を見直したところ、`discord_search` 1 回ごとにエージェントのターンが 1 つ増え
(実測で約 2.4 秒)、返した抜粋(最大 20 件 × 300 字)が以降のターンで毎回送り直されることが分かった。
呼び出し回数を抑えているのはプロンプトの「1〜2 回」という指示だけで、コードの上限は無い。
また初回の取り込み(D3)は 1 件ずつ自動コミットで保存するため、1 チャンネル最大 10,000 件の書き込みが
イベントループを塞ぎ、取り込み中の /ask や Gateway のイベント処理が遅れる。

### 決定

- **A1. ツールの呼び出し回数をコードで制限する**: `max_tool_calls`(既定 1・0〜5)。/ask 1 件ごとのセッションで
  数え、上限を超えた呼び出しは検索せずに短い定型文(「検索の上限(1 回)に達しました。手元の根拠で回答してください。」)
  を返す。数えるのは**実際にストアを検索した回数**で、引数の誤り(日付の形式・解決できないチャンネル)は
  数えない(言い直しの 1 回を奪わないため。ターン数は従来どおり `maxTurns` が抑える)。
  - `0` はツールを**渡さない**(`mcpServers` にも載らない)。ただし機能は ON のままなので、D7 の
    「今回ツールが返した permalink だけを受け付ける」はそのまま効く(返した permalink が無いので Discord の引用は
    すべて破棄される)。OFF の形式検証に緩むことはない。
  - プロンプト(qa/answer)の「1 回まで」とコードの上限の二重にする(プロンプトだけでは守られない)。
- **A2. 1 回の検索で渡す量を減らす**: `max_results` の既定を 20 → **8**(上限 100 は据え置き)。
  抜粋の長さを定数から設定 `excerpt_chars`(既定 **200**・80〜500)に移す。最初に一致した語の周辺を切り出す
  方式は変えない。8 × 200 字で、従来の約 1/4 の量になる。
- **A3. 事前検索の受け皿として OR 検索をストアに足す**(`searchAny`): 3 文字以上の語を FTS のフレーズとして
  **OR** で結び、bm25 の候補を多めに取ってから、各候補の本文に含まれる語の数(2 文字以下の語も含む・大小無視)を
  JS で数え、(一致した語の数の多い順 → bm25 → 新しい順)で並べて上限件数を返す。3 文字以上の語が無いときは
  短い語の LIKE の OR で候補を取る(bm25 は無し)。
  - 検索範囲の絞り込みは `search` と同じ(親チャンネルが「質問者に見える ∩ いま bot に見える」集合にあるものだけ。
    空なら 0 件)。呼び出し元は D5 の検索範囲を渡すこと。SQL は固定で、語はフレーズ・LIKE のパラメータとしてだけ渡る。
  - 既存の `search`(ツールが使う AND 検索)の挙動は変えない。
  - **事前検索そのもの(いつ・何件をモデルに渡すか)と関連度ゲートは ADR-0041「System One 判定層」で決める。**
    本 ADR の「却下した代替案」の「検索結果を system prompt に事前に詰める」(質問に関係ない本文まで毎回渡す)を、
    **関連度ゲートで無関係な本文を渡さないことを条件に**見直す。ゲートを通らない本文はモデルに渡さず、
    渡した本文の permalink は D7 の検証集合に入れる(ツールが返したものと同じ扱い)ことを ADR-0041 の前提とする。
    本追記の時点では呼び出し元は無く、/ask の挙動は A1・A2 以外変わらない。
- **A4. 取り込みの書き込みをまとめる**: 1 チャンネル分の取得結果を 100 件ずつ 1 トランザクション
  (better-sqlite3 の `db.transaction`)で保存し(`upsertMany`)、塊の間で `setImmediate` によりイベントループに
  処理を返す。FTS は従来どおりトリガで同じトランザクション内に更新される(外部コンテンツ表と本文がずれない)。
  - 塊の間に届いたライブイベントとの競合は従来の規則で解決する(編集は `edited_at` の比較で巻き戻さない・
    削除は tombstone で復活しない)。加えて、同期の周期中に `ChannelDelete` / `ThreadDelete` や
    対象外への `ChannelUpdate` で消したチャンネル(とそのスレッド)は、その周期の残りの書き込みを打ち切る
    (消した直後に古い取得結果で書き戻さない)。

### 設定(D9 の表への追加・変更)

| キー | 既定 | 理由 |
|---|---|---|
| `max_tool_calls` | 1 | 呼び出し 1 回ごとにターン 1 つ(約 2.4 秒)と抜粋の再送が増える。0 = ツールを渡さない |
| `max_results` | 8(旧 20) | 1 回で渡す本文量の上限。プロンプトの再送量と露出面を抑える |
| `excerpt_chars` | 200(旧 定数 300) | 抜粋 1 件の上限。80〜500 |

### 観測

- `/ask: 完了` の `discordSearch` に `ms`(ツールが検索に使った時間の合計)と `overLimit`(上限で断った
  呼び出しの数)を加える(`calls` は実際に検索した回数・`hits` は返した件数のまま)。
  未決事項 7 は実装済み(完了ログに出ている)。
- 有効化の前後で `/ask: 完了` の `totalMs`・`numTurns`・`discordSearch.calls` / `ms` を比べる
  (runbook `discord-index-rollout.md` §2「速さの確認」)。

### ロールバック(D10 に先立つ段階)

1. `max_tool_calls: 0` で再起動(同期と保存は続け、/ask にツールを渡さない。Discord の引用は破棄される)。
2. それでも足りなければ従来どおり `enabled: false`(D10)。
- `max_results` / `excerpt_chars` は値を戻すだけでよい(保存形式は変わらない)。A4 は設定を持たず、
  保存の結果は 1 件ずつの保存と同じ(DB の互換性に影響しない)。
